This document records the profile manifest PM-001 and the preceding architecture decisions for TETOOLS.ADMIN_OBJECTS. The platform scope is Oracle Database 19c Enterprise. It is a design reference for this module and for later TETOOLS modules. It does not define an installed implementation.

PM-001-09Serialization and fingerprint identityMixed

Historical baseline (revision 001/002). Current decisions and code are in revision 003, chapters 28-35. Earlier proposals/code are retained for traceability.

Revisie 002 — leidende reviewverwerking (Mixed)

G: exacte canonieke bytes zijn als principe akkoord. Het protocol POC_TLV_1 hieronder is uitsluitend een testvoorstel, geen goedgekeurd productieprotocol. PoC gebruikt STANDARD_HASH op RAW met een harde grens van 2000 bytes voor de volledige invoer; geen afkapping. Een productiepad met DBMS_CRYPTO moet vooraf door DBA worden voorzien van directe GRANT EXECUTE ON SYS.DBMS_CRYPTO TO voor definer-rights-code; alleen een rol volstaat daarvoor niet. Deze PoC vereist geen DBMS_CRYPTO-grant.

Oorspronkelijke tekst hieronder blijft als context; bij verschil geldt dit revisieblok.

Basis: [S10] [S11]

PM-001 proposal: serialize each field with unambiguous type and byte-length encoding. Encode text as UTF-8. Use different codes for null and not applicable. Encode numbers without NLS-dependent formatting. Fully order records and encode repeated membership so that adding or removing a component changes the canonical input.

Comparison context =
  PROFILE_CODE + PROFILE_VERSION + CANONICAL_VERSION
  + HASH_ALGORITHM + FINGERPRINT

Canonical input = profile header + ordered typed records
Fingerprint    = hash(complete canonical input)

Administrative descriptions, timestamps, inventory display and severity do not enter canonical input. The inventory is not hashed. Owner and object name were proposed to remain outside the configuration hash so that equivalent selected configurations in different environments can compare. Their registry identity remains separate. This exclusion is still a proposal.

Open: the exact bytes are not yet approved. Define type tags, length width, byte order, record framing, header fields, null/N/A tokens, integer rules, sorting and overflow handling before storing accepted production hashes. A pipe-delimited or readable JSON example is not the canonical protocol. No fabricated example digest is presented as a PM-001 result.

Technical note: STANDARD_HASH in Oracle 19c supports SHA256 and returns RAW. Its input cannot be LONG or a LOB; the default algorithm is SHA1, so the algorithm must be explicit. DBMS_CRYPTO supports LOB hashing and SHA-256, with package-access considerations. These are alternative implementation paths, not a final choice.[O-HASH] [O-CRYPTO]

For the PoC, PM-001 proposes a bounded complete input and a hard failure on overflow. Production must hash the complete byte representation without truncation. A UTF-8 byte BLOB is a candidate for a large-input path; prove conversion, permissions and RAW output formatting in Oracle before adoption. Independent chunk hashes must not silently replace the agreed whole-input hash.

Preflight checks the offered delivery, object versions, historical fingerprints and confidence in the existing fingerprints. It reports blocking and non-blocking findings before installation DDL. A blocking outcome prevents release to execution. Reporting a drift finding does not automatically create a new compulsory manual approval for every installation.

Execution follows the applicable release decision and installation rules. After creation or modification, calculate and compare the actual target fingerprint. The administrator remains responsible for the operational decision. A new configuration fingerprint supports the comparison but does not prove that the delivery is good.

Open: how to handle object changes between preflight and execution, failed post-install comparison, partial success and retry requires a concrete execution protocol. A recheck before execution is a proposal, not an existing guarantee.

# TETOOLS ADMIN\_OBJECTS — Definitie profielmanifest

Ontwerpvoorstel PM-001 · Oracle Database 19c Enterprise · PoC-fase

Op basis van onze afspraken stel ik een **versiegebonden, declaratief profielmanifest** voor. Het profiel beschrijft welke onderdelen van een Oracle-object onderzocht worden, hoe hun metadata wordt genormaliseerd en hoe daaruit een reproduceerbaar objectmanifest ontstaat.

De belangrijkste ontwerpkeuze is dat het profielmanifest **geen vast sjabloon is waarin ieder mogelijk onderdeel verplicht voorkomt**\. Het is een verzameling regels die bepaalt welke componenten en eigenschappen relevant zijn voor een bepaalde objectcategorie.

Dat maakt het mogelijk dezelfde structuur later te gebruiken voor tabellen, indexen, packages, sequences, views en andere objecttypen, zonder dat we die nu allemaal hoeven te implementeren.

## 1\. Afbakening van de drie registraties

| Registratie | Inhoud | Opslag |
|--------|--------|--------|
| **Profielmanifest** | Definities, metadataherkomst, normalisatieregels en profielversie | Permanent, versiegebonden |
| **Objectmanifest** | De daadwerkelijke genormaliseerde eigenschappen van één object | Ad hoc gegenereerd; niet standaard permanent |
| **Componentinventaris** | Minimale lijst van aanwezige componenttypen en identiteiten | Bij succesvolle installatie of relevante afwijkende herberekening |

De componentinventaris is uitsluitend diagnostisch. Zij is geen invoer voor de fingerprint.

### Afhandeling na een afwijking

Ik neem ook je laatste correctie op\:

- **Accepteren van nieuwe werkelijkheid\:** de beheerder accepteert de nieuw waargenomen fingerprint en inventaris. Na registratie van besluit en handeling vervangen deze de eerder geaccepteerde waarden.
- **Corrigerende herinstallatie\:** de beheerder kiest voor herinstallatie, eventueel met een expliciete uitzondering. Na een succesvolle installatie en verificatie worden de twee eerdere actieve registraties vervangen door de nieuwe.

In beide gevallen blijft de vastlegging van het beheerdersbesluit en de uitgevoerde handeling beschikbaar als auditinformatie. De eerdere componentinventarissen hoeven daarna niet als actieve vergelijkingsregistraties te blijven bestaan.

Dit is opslag- en afhandelingsbeleid, geen onderdeel van het profielmanifest zelf.

---

## 2\. Logische structuur van het profielmanifest

Ik stel vijf onderdelen voor.

**01 — PROFILE**

Identiteit, versie, objectcategorie en status

**02 — COMPONENT**

Welke soorten onderdelen kunnen aanwezig zijn?

**03 — PROPERTY**

Welke eigenschappen van elk onderdeel tellen mee?

**04 — NORMALIZATION**

Hoe worden waarden, afwezigheid, volgorde en datatypes behandeld?

**05 — SERIALIZATION**

Hoe worden de genormaliseerde records deterministisch gecodeerd?

Deze vijf onderdelen zijn logische groepen. Ze vereisen niet noodzakelijk vijf fysieke databasetabellen.

## 6\. NORMALIZATION — Normalisatieregels

De normalisatieregels moeten onafhankelijk zijn van de specifieke tabel die wordt onderzocht.

| Regel | Gedrag |
|--------|--------|
| `IDENTIFIER_EXACT` | Dictionarynaam behouden, inclusief hoofdlettergebruik |

| `ORDER_IDENTITY` | Op stabiele componentidentiteit sorteren |
| `PRESENCE_FLAG` | Aanwezigheid of afwezigheid expliciet vastleggen |

De normalisatie moet bovendien onderscheid maken tussen drie situaties\:

| Situatie | Interpretatie |
|--------|--------|
| Eigenschap heeft een NULL-waarde | Geldige metadatawaarde, indien toegestaan |
| Eigenschap is niet van toepassing | Geldige uitkomst volgens het profiel |

Voor de PoC stel ik voor om uitsluitend vooraf bekende normalisatieregels te ondersteunen. Het profielmanifest verwijst naar deze regels via codes; het bevat geen vrij uitvoerbare SQL of PL/SQL.

### Bijzondere aandacht: inline componenten

Het profiel kan actuele constraints, indexen en andere componenten herkennen via de Oracle Data Dictionary. Het kan echter niet zonder aanvullende informatie betrouwbaar vaststellen of een constraint oorspronkelijk inline in `CREATE TABLE` of later met `ALTER TABLE` is aangemaakt.

Daarom moeten we de reikwijdte van een tabelfingerprint definiëren op basis van **actuele metadata en expliciete profielregels**, niet op basis van veronderstelde DDL-herkomst.

Voor zelfstandig beheerde indexen blijft een eigen fingerprint het uitgangspunt. Welke door Oracle gegenereerde ondersteunende indexen in een tabelfingerprint vallen, moet per profiel expliciet worden bepaald.

Dit is een nog te toetsen grensgeval, geen reden om een afzonderlijke relatiesadministratie te introduceren.

## 7\. SERIALIZATION — Canonieke gegevensrepresentatie

De canonieke representatie wordt uit de genormaliseerde objectrecords opgebouwd.

De sortering wordt volledig bepaald door het profiel\:

```text
PROFILE_ID
PROFILE_VERSION
CANONICAL_VERSION

COMPONENT_ID
COMPONENT_IDENTITY
COMPONENT_POSITION
PROPERTY_ID
VALUE_TYPE
VALUE
```

Voor de daadwerkelijke hashinput geldt\:

- Ieder veld krijgt een ondubbelzinnige type- en lengtecodering.
- Tekst wordt als UTF-8 gecodeerd; lengtes worden in bytes bepaald.
- NULL en niet-toepasbaar krijgen verschillende codes.
- Numerieke waarden krijgen een vaste, NLS-onafhankelijke representatie.
- De volgorde van records is expliciet en reproduceerbaar.
- Dubbele componentidentiteiten of ongeldige metadata veroorzaken een fout, geen gedeeltelijke fingerprint.

De serializer moet daarnaast de **aanwezigheid van herhaalde componenten** ondubbelzinnig vastleggen. Daardoor kan een object met drie kolommen niet dezelfde canonieke invoer krijgen als een object met vier kolommen.

Voor de PoC blijft een begrensde invoer met een harde fout bij overschrijding acceptabel. Voor productie moet de volledige canonieke invoer zonder afkapping kunnen worden gehasht, ook wanneer deze groter is dan een gewone SQL-string.

Volgens jouw laatste keuze bevat de componentinventaris uitsluitend het componenttype en de identiteit van daadwerkelijk aanwezige componenten.

Dit is uitsluitend een voorbeeld. Welke indexen in de inventaris van een tabelberekening verschijnen, volgt uit de geselecteerde profielregels.

We hebben nu het logische profielmanifest gedefinieerd. De volgende stap is niet onmiddellijk de volledige PL/SQL-generator, maar de vertaling naar een **klein fysiek datamodel**\.

Voorlopig byteprotocol

POC_TLV_1: ieder token is N (hex 4E) voor Oracle NULL, of V + acht hoofdletter hex ASCII-cijfers voor AL32UTF8-bytelengte + : + payload. Voorbeeld A = hex 5630303030303030313A41. A en N hebben een NULL-waardetoken, maar verschillende toestandtokens. Geen Unicode-normalisatie. Alle integers TM9 met vaste NLS-instelling; uitsluitend metadata-integers. Owner/rootnaam, inventory, tijd en presentatie tellen niet mee. De grens van 2000 bytes is een PoC-beperking, geen beperking van SHA-256 zelf.

 function frame(p_value varchar2) return raw is
  r raw(32767); b raw(32767);
 begin
  -- NULL token N; value token V + 8 ASCII hex byte-length digits + ':' + UTF8.
  -- No delimiter escaping needed: lengths delimit payloads. Oracle '' = NULL.
  if p_value is null then return hextoraw('4E'); end if;
  b:=utl_i18n.string_to_raw(p_value,'AL32UTF8');

  r:=utl_i18n.string_to_raw('V'||lpad(to_char(utl_raw.length(b),'FMXXXXXXXX'),8,'0')||':','AL32UTF8');

Release linkage

AO3_RELEASE holds the offered JSON separately from actual installer and execution outcome. AO3_FP links individual TABLE, INDEX and CONSTRAINTS observations to release_id + owner + actual identity + type and stores profile tuple, CON_ID, observed timestamp, digest and full objectmanifest. Child index/constraint digests are computed from their own canonical records, never from the table hash. AO3_POC.STORE_OBSERVATIONS coordinates persistence after one extraction. It creates no commit and rolls its set back on failure; an already-used key fails visibly instead of overwriting a reference.

These tables are a PoC schema, not an approved production retention model. A stored observation is not automatically an ACCEPTED baseline. Production must distinguish observations from accepted references and preserve both after divergence. Freshness is not inferred solely from LAST_DDL_TIME or elapsed time. Recalculate when reliability is insufficient; exact criteria remain open.
