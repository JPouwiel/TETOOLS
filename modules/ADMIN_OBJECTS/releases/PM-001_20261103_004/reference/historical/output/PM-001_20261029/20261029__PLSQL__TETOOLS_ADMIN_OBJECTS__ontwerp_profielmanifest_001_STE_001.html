PM-001-01Purpose, scope and reading rulesAgreed

Basis: [S01] [S02] [S03] [S10]

This document records the profile manifest PM-001 and the preceding architecture decisions for TETOOLS.ADMIN_OBJECTS. The platform scope is Oracle Database 19c Enterprise. It is a design reference for this module and for later TETOOLS modules. It does not define an installed implementation.

The fingerprint supports installation checks and the detection of configuration changes. It reduces repeated work when an object already exists. It does not identify a release by itself. It does not certify the quality of a delivery or replace the developer or administrator.

LabelMeaning
AgreedAn explicit user decision, or an agreed design direction. The cited source determines the scope.
ProposalA concrete design from the earlier conversation, or a clearly marked implementation recommendation. It is not an approved database contract.
OpenA policy or technical choice still needs a decision or a test.
MixedThe chapter contains items with different statuses. Each item identifies its status.
Technical noteAn Oracle 19c fact or an engineering implication, with a source. It does not create a new project agreement.

The document uses clear English inspired by ASD-STE100. No formal compliance or measured percentage is claimed. Code and record examples use Courier New, 11 pt. Navy identifies headings; turquoise identifies navigation and accents. Status labels contain text as well as colour. No code replacement, addition or deletion colours are used because no existing code is changed.

PM-001-03Object scope and optional or repeated componentsMixed

Basis: [S06] [S07] [S10]

Agreed: the design must support different object categories, optional components and repeated components. Each independently managed object has its own fingerprint. The profile defines which internal components belong to its scope. Do not create an independent relationship or dependency registry.

Object family reported by the userDesign treatmentImplementation status
Tables; table partitions; LOBs; LOB partitionsA table profile can include selected internal structure. Presence and applicable details must be explicit.Table PoC only; exact extended scope open.
Indexes; index partitionsAn independently managed index has its own profile and fingerprint. Supporting indexes require an explicit profile boundary.Not implemented.
Packages: specification and body; one specification used for types without a bodyThe profile must represent the supported object shape; do not assume that every specification has a body.Specification/body grouping open.
Functions; procedures; triggers; types; views; materialized views; sequencesSeparate managed object categories. Do not infer all related objects into a table fingerprint.Future profile definitions.
Database links; jobs; queuesReported objects in the schema; identity and metadata extraction need category-specific design.Future profile definitions.

Technical interpretation: present dictionary metadata describes current constraints and supporting indexes. It is insufficient evidence of the original inline versus later ALTER TABLE syntax. Define membership by explicit current-metadata rules; do not reconstruct DDL provenance from object names.[O-CON]

Open: constraint identity, generated index inclusion, duplicate semantic constraints, partitions, subpartitions and LOB details require exact rules. An unsupported object shape must be visible as unsupported; it must not receive a misleading complete-coverage label. This last rule is a proposed implementation safeguard.

Basis: [S10] [S11]

PM-001 proposes five logical groups: PROFILE, COMPONENT, PROPERTY, NORMALIZATION and SERIALIZATION. These groups do not require five physical tables. The following fields reproduce the PM-001 proposal; physical lengths, constraints and storage are not approved.

PROFILE fieldLogical typeExampleRequired in proposal
PROFILE_CODEVARCHAR2TABLE_COREYes
PROFILE_VERSIONNUMBER1Yes
PROFILE_NAMEVARCHAR2Table core structureYes
OBJECT_TYPEVARCHAR2TABLEYes
SUBJECTVARCHAR2Table metadataYes
DESCRIPTIONVARCHAR2 / CLOBFunctional explanationYes
CANONICAL_VERSIONNUMBER1Yes
HASH_ALGORITHMVARCHAR2SHA256Yes
PROFILE_STATUSVARCHAR2DRAFTYes

The logical key is (PROFILE_CODE, PROFILE_VERSION). Once a profile version supports accepted fingerprints, its interpretation rules remain immutable. A changed interpretation requires a new profile version. Administrative name, subject and description do not enter the hash. Open terminology: earlier examples use PROFILE_ID and CANONICAL_FORMAT_VERSION. PM-001 uses PROFILE_CODE and CANONICAL_VERSION. Use the logical profile key for portable comparison; a physical surrogate ID must not silently change the hash between environments. This is a proposed clarification, not a settled schema change.

PM-001-09Serialization and fingerprint identityMixed

Basis: [S10] [S11]

PM-001 proposal: serialize each field with unambiguous type and byte-length encoding. Encode text as UTF-8. Use different codes for null and not applicable. Encode numbers without NLS-dependent formatting. Fully order records and encode repeated membership so that adding or removing a component changes the canonical input.

Comparison context =
  PROFILE_CODE + PROFILE_VERSION + CANONICAL_VERSION
  + HASH_ALGORITHM + FINGERPRINT

Canonical input = profile header + ordered typed records
Fingerprint    = hash(complete canonical input)

Administrative descriptions, timestamps, inventory display and severity do not enter canonical input. The inventory is not hashed. Owner and object name were proposed to remain outside the configuration hash so that equivalent selected configurations in different environments can compare. Their registry identity remains separate. This exclusion is still a proposal.

Open: the exact bytes are not yet approved. Define type tags, length width, byte order, record framing, header fields, null/N/A tokens, integer rules, sorting and overflow handling before storing accepted production hashes. A pipe-delimited or readable JSON example is not the canonical protocol. No fabricated example digest is presented as a PM-001 result.

Technical note: STANDARD_HASH in Oracle 19c supports SHA256 and returns RAW. Its input cannot be LONG or a LOB; the default algorithm is SHA1, so the algorithm must be explicit. DBMS_CRYPTO supports LOB hashing and SHA-256, with package-access considerations. These are alternative implementation paths, not a final choice.[O-HASH] [O-CRYPTO]

For the PoC, PM-001 proposes a bounded complete input and a hard failure on overflow. Production must hash the complete byte representation without truncation. A UTF-8 byte BLOB is a candidate for a large-input path; prove conversion, permissions and RAW output formatting in Oracle before adoption. Independent chunk hashes must not silently replace the agreed whole-input hash.

PM-001-10Minimal component inventoryAgreed

Basis: [S07] [S08] [S09] [S10]

Store only the component type and identity of components present in the calculation scope. The user explicitly accepted the minimal level. Earlier examples with datatype, precision and length are superseded. Do not include absence lines such as PARTITIONED=NO.

OBJECT: TETOOLS.ADMIN_LOGGER_LOG
PROFILE: TABLE_CORE / 1

TABLE       ADMIN_LOGGER_LOG
COLUMN      LOG_ID
COLUMN      LOG_MESSAGE
CONSTRAINT  PK_ADMIN_LOGGER_LOG

This is an illustrative display. The selected profile decides whether the shown constraint belongs in the calculation. An index may appear only when that profile includes it. Object/profile/calculation linkage is context for the inventory; it does not expand each component entry with attributes.

Build the inventory from the same metadata extraction as the object manifest and fingerprint. Store it after a successful installation and calculation. After a successful recalculation, store a separate observed inventory when the fingerprint differs from the accepted reference. Keep both until a corrective action is completed.

The inventory can explain added or removed identities. It cannot reconstruct an old precision or expression when the component identity stays the same. A changed fingerprint with an unchanged inventory is valid and expected. The developer retains detailed change information in source version control.

Basis: [S08] [S09]

Preflight checks the offered delivery, object versions, historical fingerprints and confidence in the existing fingerprints. It reports blocking and non-blocking findings before installation DDL. A blocking outcome prevents release to execution. Reporting a drift finding does not automatically create a new compulsory manual approval for every installation.

Execution follows the applicable release decision and installation rules. After creation or modification, calculate and compare the actual target fingerprint. The administrator remains responsible for the operational decision. A new configuration fingerprint supports the comparison but does not prove that the delivery is good.

Oracle issues implicit commits before syntactically valid DDL and after successful DDL. Preflight reduces avoidable partial installations; it does not make all installation DDL one rollbackable transaction.[O-DDL]

Open: how to handle object changes between preflight and execution, failed post-install comparison, partial success and retry requires a concrete execution protocol. A recheck before execution is a proposal, not an existing guarantee.

PM-001-15Installation decision matrix and rule precedenceMixed

Basis: [S07] [S08] [S09]

Apply version and compatibility gates before treating a configuration as a new candidate. Resolve confidence in the existing fingerprint before comparison. The matrix preserves the user’s corrections. “Candidate” means continue the remaining checks, not unconditional permission.

IDConditionActionEvidence status
I-01Object does not exist.Install only after applicable preflight gates; calculate actual fingerprint and compare after creation.Agreed direction.
I-02Offered version is equal to or older than the registered version.Block under version policy. Exceptional reinstall/downgrade needs an explicitly defined procedure.Explicit user rule; exception details open.
I-03Offered hash is registered against an older object version.Block unless the defined explicit exception applies. Use full fingerprint context and version history.Explicit user rule; ambiguous reuse needs policy.
I-04Existing fingerprint is unreliable.Recalculate first; then continue the normal decision tree. A failed calculation is not a valid comparison.Explicit user rule.
I-05Offered version is newer; offered fingerprint is new to the module.Treat as a candidate new object configuration and continue preflight. Difference alone does not interrupt.Explicit user correction.
I-06Existing object fingerprint was recalculated and equals the offered fingerprint.Abort installation and report the finding. Do not convert this branch into automatic approval or silent skip.Explicit user correction.
I-07Recalculated existing fingerprint differs from the offered fingerprint.Treat as a candidate new configuration only when the offered version supports that conclusion. Apply remaining gates.Explicit user correction.
I-08Recalculated existing fingerprint differs from its stored accepted fingerprint.Log and report drift with references to the relevant component inventories. Keep accepted and observed evidence until corrective action.Explicit user rule; orthogonal to I-06/I-07.
I-09Fresh trusted stored fingerprint equals offered fingerprint without recalculation.An earlier assistant proposed skipping the object. The later abort rule explicitly describes recalculation. Confirm whether the no-recalculation branch should skip or abort.Open; do not silently generalise I-06.

Open conflict: one fingerprint can belong to several successful object versions. For example, versions 1.1 and 1.2 may both have Hash B. “Known older fingerprint” must not be implemented as an unqualified hash-only lookup. The precedence between strict old-configuration rejection and a legitimate newer release with unchanged selected metadata still needs a policy. PM-001 does not invent that exception.

The earlier rule “any difference between offered and stored fingerprint interrupts installation” is superseded by I-05 and I-07. The earlier “recalculated equals offered: no automatic approval” is sharpened to explicit abort by I-06. An environment drift report under I-08 remains separate from whether the offered release is newer.

PM-001-16Successful-installation history and evidenceAgreed

Basis: [S08] [S10]

Keep the fingerprints of every successful installation linked to the installed object versions. A fingerprint identifies selected configuration, not a unique release. Multiple object versions can therefore have the same fingerprint. A fingerprint must not be the sole unique key for history.

Object versionFingerprintMeaning
1.0Hash AFirst successful configuration.
1.1Hash BSelected configuration changed.
1.2Hash BVersion changed; selected configuration did not.
1.3Hash CAnother selected configuration.

Hash A/B/C are symbolic. This is not a measured database history. Record the object, version, profile identity/version, canonical format, algorithm, calculation time/result and installation context so that comparisons are interpretable. These are logical information requirements; physical tables and keys still need design.

Keep three lifecycles distinct: successful-installation fingerprint history; accepted/observed active comparison records; and decision/action audit logs. Replacing active comparison inventories after correction must not be interpreted as deleting all successful-installation history.

Open: history retention, archival, administrator identity, timestamps, links to installation logs, and the treatment of repeated installs of the same version require a physical model. Full old object manifests are not required by this agreement.

PM-001-19Broader ledger, evaluation and lifecycle contextMixed

Basis: [S12] [S08]

This chapter preserves the relevant earlier local handoff. Its scope extends beyond PM-001. Later fingerprint-specific decisions take precedence for fingerprint/inventory handling.

  • Keep the existing ledger as the basis for further design. A complete refactoring is not approved.
  • An incomplete installation delivery with missing mandatory lifecycle or removal statements is rejected; log the attempt and reason. An incomplete discovery finding can instead enter PENDING for later review. Those are different routes.
  • One module version is installed at a time. Monitoring-query versions may coexist. Whether physical object versions coexist is open.
  • Module, database, query and log-table versions have separate meanings. CURRENT need not be the highest version.
OBJECT_STATUSRecorded meaning
ACTIVEUsable under the conditions, but not the selected version.
CURRENTSelected/in use; not necessarily the highest version.
INACTIVEExplicitly taken out of use, for example due to a bug.
FUTURE RELEASENeeds newer applicable module/database versions.
DEPRECATEDToo old for current applicable versions.
PENDINGDiscovered registration still requires processing and review.
ERRORAn error condition, such as missing required objects or Oracle INVALID; report it.

Design direction: keep OBJECT_STATUS and use EVALUATION_STATUS values ACCEPTED, REJECTED and PENDING. Administrator acceptance does not override ERROR, INACTIVE or unmet applicability conditions. CURRENT + ACCEPTED is the proposed executable combination while its conditions hold.

Previously reviewed registrations, including CURRENT, are rechecked. A relevant change returns evaluation to PENDING. Already PENDING evaluations are not repeatedly reopened in subsequent inventory rounds. The ledger keeps the latest evaluation/re-evaluation data; further reasons can remain in logs until log cleanup. Full evaluation history was not required.

Open: evaluation transitions, EVALUATED/REEVALUATED field updates, changes that invalidate acceptance, ongoing observation of PENDING items, CURRENT selection and reopening INACTIVE/REJECTED. These are not implemented by this document. The evaluation-history limit does not cancel the later successful-installation fingerprint-history agreement.

# TETOOLS ADMIN\_OBJECTS — Definitie profielmanifest

Ontwerpvoorstel PM-001 · Oracle Database 19c Enterprise · PoC-fase

Op basis van onze afspraken stel ik een **versiegebonden, declaratief profielmanifest** voor. Het profiel beschrijft welke onderdelen van een Oracle-object onderzocht worden, hoe hun metadata wordt genormaliseerd en hoe daaruit een reproduceerbaar objectmanifest ontstaat.

De belangrijkste ontwerpkeuze is dat het profielmanifest **geen vast sjabloon is waarin ieder mogelijk onderdeel verplicht voorkomt**\. Het is een verzameling regels die bepaalt welke componenten en eigenschappen relevant zijn voor een bepaalde objectcategorie.

Dat maakt het mogelijk dezelfde structuur later te gebruiken voor tabellen, indexen, packages, sequences, views en andere objecttypen, zonder dat we die nu allemaal hoeven te implementeren.

## 1\. Afbakening van de drie registraties

| Registratie | Inhoud | Opslag |
|--------|--------|--------|
| **Profielmanifest** | Definities, metadataherkomst, normalisatieregels en profielversie | Permanent, versiegebonden |
| **Objectmanifest** | De daadwerkelijke genormaliseerde eigenschappen van één object | Ad hoc gegenereerd; niet standaard permanent |
| **Componentinventaris** | Minimale lijst van aanwezige componenttypen en identiteiten | Bij succesvolle installatie of relevante afwijkende herberekening |

De componentinventaris is uitsluitend diagnostisch. Zij is geen invoer voor de fingerprint.

### Afhandeling na een afwijking

Ik neem ook je laatste correctie op\:

- **Accepteren van nieuwe werkelijkheid\:** de beheerder accepteert de nieuw waargenomen fingerprint en inventaris. Na registratie van besluit en handeling vervangen deze de eerder geaccepteerde waarden.
- **Corrigerende herinstallatie\:** de beheerder kiest voor herinstallatie, eventueel met een expliciete uitzondering. Na een succesvolle installatie en verificatie worden de twee eerdere actieve registraties vervangen door de nieuwe.

In beide gevallen blijft de vastlegging van het beheerdersbesluit en de uitgevoerde handeling beschikbaar als auditinformatie. De eerdere componentinventarissen hoeven daarna niet als actieve vergelijkingsregistraties te blijven bestaan.

Dit is opslag- en afhandelingsbeleid, geen onderdeel van het profielmanifest zelf.

---

## 2\. Logische structuur van het profielmanifest

Ik stel vijf onderdelen voor.

**01 — PROFILE**

Identiteit, versie, objectcategorie en status

**02 — COMPONENT**

Welke soorten onderdelen kunnen aanwezig zijn?

**03 — PROPERTY**

Welke eigenschappen van elk onderdeel tellen mee?

**04 — NORMALIZATION**

Hoe worden waarden, afwezigheid, volgorde en datatypes behandeld?

**05 — SERIALIZATION**

Hoe worden de genormaliseerde records deterministisch gecodeerd?

Deze vijf onderdelen zijn logische groepen. Ze vereisen niet noodzakelijk vijf fysieke databasetabellen.

## 3\. PROFILE — Profielidentiteit

| Eigenschap | Type | Voorbeeld | Verplicht |
|--------|--------|--------|--------|
| `PROFILE_CODE` | VARCHAR2 | `TABLE_CORE` | Ja |
| `PROFILE_VERSION` | NUMBER | `1` | Ja |
| `PROFILE_NAME` | VARCHAR2 | `Table core structure` | Ja |
| `OBJECT_TYPE` | VARCHAR2 | `TABLE` | Ja |
| `SUBJECT` | VARCHAR2 | `Table metadata` | Ja |
| `DESCRIPTION` | VARCHAR2/CLOB | Functionele toelichting | Ja |
| `CANONICAL_VERSION` | NUMBER | `1` | Ja |
| `HASH_ALGORITHM` | VARCHAR2 | `SHA256` | Ja |
| `PROFILE_STATUS` | VARCHAR2 | `DRAFT` | Ja |

Een profiel wordt geïdentificeerd door de combinatie `PROFILE_CODE` en `PROFILE_VERSION`\.

Zodra een profielversie wordt gebruikt voor geaccepteerde fingerprints, worden de inhoudelijke regels ervan onveranderlijk. Een gewijzigde interpretatie krijgt een nieuwe profielversie.

Naam, onderwerp en beschrijving zijn administratieve metadata en beïnvloeden de fingerprint niet. De profielcode, profielversie en canonieke formaatversie maken wel deel uit van de canonieke header.

## 4\. COMPONENT — Definitie van componentcategorieën

Een component is hier een logisch onderdeel van het onderzochte hoofdobject, niet noodzakelijk een zelfstandig Oracle-schemaobject.

| Veld | Betekenis |

| `COMPONENT_CODE` | Bijvoorbeeld `COLUMN`, `CONSTRAINT`, `PARTITION` |
| `PARENT_COMPONENT_ID` | Optioneel, voor geneste componenttypen |
| `SOURCE_CODE` | Identificatie van een toegestane metadata-extractor |
| `MIN_OCCURS` | Minimumaantal componenten |
| `MAX_OCCURS` | Maximumaantal, eventueel onbeperkt |
| `IDENTITY_RULE` | Regel om individuele componenten te identificeren |
| `ORDER_RULE` | Regel voor deterministische volgorde |
| `ABSENCE_RULE` | Betekenis van afwezigheid |
| `DESCRIPTION` | Documentatie |

## 6\. NORMALIZATION — Normalisatieregels

De normalisatieregels moeten onafhankelijk zijn van de specifieke tabel die wordt onderzocht.

| Regel | Gedrag |
|--------|--------|
| `IDENTIFIER_EXACT` | Dictionarynaam behouden, inclusief hoofdlettergebruik |
| `INTEGER_DECIMAL` | Getal zonder NLS-afhankelijke notatie |
| `ENUM_UPPER` | Waarde normaliseren naar een toegestane hoofdlettercode |
| `NULL_EXPLICIT` | NULL afzonderlijk coderen |
| `NOT_APPLICABLE` | Niet-toepasselijke eigenschap volgens profielregel behandelen |
| `ORDER_POSITION` | Functionele volgorde behouden |
| `ORDER_IDENTITY` | Op stabiele componentidentiteit sorteren |
| `PRESENCE_FLAG` | Aanwezigheid of afwezigheid expliciet vastleggen |

De normalisatie moet bovendien onderscheid maken tussen drie situaties\:

| Situatie | Interpretatie |
|--------|--------|
| Eigenschap heeft een NULL-waarde | Geldige metadatawaarde, indien toegestaan |
| Eigenschap is niet van toepassing | Geldige uitkomst volgens het profiel |
| Metadata kon niet worden vastgesteld | Extractie- of validatiefout |

Voor de PoC stel ik voor om uitsluitend vooraf bekende normalisatieregels te ondersteunen. Het profielmanifest verwijst naar deze regels via codes; het bevat geen vrij uitvoerbare SQL of PL/SQL.

### Bijzondere aandacht: inline componenten

Het profiel kan actuele constraints, indexen en andere componenten herkennen via de Oracle Data Dictionary. Het kan echter niet zonder aanvullende informatie betrouwbaar vaststellen of een constraint oorspronkelijk inline in `CREATE TABLE` of later met `ALTER TABLE` is aangemaakt.

Daarom moeten we de reikwijdte van een tabelfingerprint definiëren op basis van **actuele metadata en expliciete profielregels**, niet op basis van veronderstelde DDL-herkomst.

Voor zelfstandig beheerde indexen blijft een eigen fingerprint het uitgangspunt. Welke door Oracle gegenereerde ondersteunende indexen in een tabelfingerprint vallen, moet per profiel expliciet worden bepaald.

Dit is een nog te toetsen grensgeval, geen reden om een afzonderlijke relatiesadministratie te introduceren.

## 7\. SERIALIZATION — Canonieke gegevensrepresentatie

De canonieke representatie wordt uit de genormaliseerde objectrecords opgebouwd.

De sortering wordt volledig bepaald door het profiel\:

```text
PROFILE_ID
PROFILE_VERSION
CANONICAL_VERSION

COMPONENT_ID
COMPONENT_IDENTITY
COMPONENT_POSITION
PROPERTY_ID
VALUE_TYPE
VALUE
```

Voor de daadwerkelijke hashinput geldt\:

- Ieder veld krijgt een ondubbelzinnige type- en lengtecodering.
- Tekst wordt als UTF-8 gecodeerd; lengtes worden in bytes bepaald.
- NULL en niet-toepasbaar krijgen verschillende codes.
- Numerieke waarden krijgen een vaste, NLS-onafhankelijke representatie.
- De volgorde van records is expliciet en reproduceerbaar.
- Dubbele componentidentiteiten of ongeldige metadata veroorzaken een fout, geen gedeeltelijke fingerprint.

De serializer moet daarnaast de **aanwezigheid van herhaalde componenten** ondubbelzinnig vastleggen. Daardoor kan een object met drie kolommen niet dezelfde canonieke invoer krijgen als een object met vier kolommen.

Voor de PoC blijft een begrensde invoer met een harde fout bij overschrijding acceptabel. Voor productie moet de volledige canonieke invoer zonder afkapping kunnen worden gehasht, ook wanneer deze groter is dan een gewone SQL-string.

## 8\. Minimale componentinventaris

Volgens jouw laatste keuze bevat de componentinventaris uitsluitend het componenttype en de identiteit van daadwerkelijk aanwezige componenten.

Bijvoorbeeld\:

```text
OBJECT: TETOOLS.ADMIN_LOGGER_LOG

COLUMN      LOG_ID
```

Dit is uitsluitend een voorbeeld. Welke indexen in de inventaris van een tabelberekening verschijnen, volgt uit de geselecteerde profielregels.

Er worden geen ontbrekende componenten vermeld en geen aanvullende attributen zoals precisie, nullable of opslagparameters opgenomen.

De inventaris wordt afgeleid uit dezelfde extractie als het objectmanifest. Bij een afwijkende herberekening blijven de oorspronkelijke en nieuwe inventaris beschikbaar tot een corrigerende actie is afgerond.

## 10\. Ontwerpbesluiten en resterende afbakening

We hebben nu het logische profielmanifest gedefinieerd. De volgende stap is niet onmiddellijk de volledige PL/SQL-generator, maar de vertaling naar een **klein fysiek datamodel**\.

Daarbij stel ik voor\:

- Profielheader en component-/eigenschapsregels permanent opslaan.
- Normalisatieregels voorlopig als vaste, bekende codes implementeren.
- Objectmanifesten in geheugen of tijdelijk opbouwen.
- Componentinventarissen alleen bewaren volgens de afgesproken installatie- en afwijkingsregels.
- Fingerprinthistorie, pakbon en beheerdersbesluiten buiten de eerste normalisatie-PoC houden, maar hun koppelingen wel in het gegevensmodel mogelijk maken.

Er blijven twee relevante keuzes voor de concrete PoC: de exacte scope van constraints en indexen binnen het eerste tabelprofiel, en de definitieve bytecodering van het canonieke formaat.

## Registratie en inventarisatie

Registraties worden doorgaans door een beheerder geladen via installatiescripts. Een onvolledige installatie-aanlevering met ontbrekende verplichte lifecycleinformatie of vereiste beheer-/verwijderstatements wordt afgewezen en niet gedeeltelijk als componentregistratie opgeslagen.

Periodieke inventarisatie ontdekt onder meer niet correct opgeruimde of geregistreerde objecten en rapporteert die voor beheerafhandeling. Een onvolledige inventarisatiebevinding mag als PENDING worden opgenomen en later worden aangevuld en beoordeeld. Dit is een andere route dan het accepteren van een onvolledig installatiepakket.

## Betekenis OBJECT_STATUS volgens de gebruiker

| Status | Betekenis |
|---|---|
| ACTIVE | Bruikbaar binnen de voorwaarden, maar niet de gekozen/in gebruik zijnde versie. |
| CURRENT | De versie die actief in gebruik is; niet noodzakelijk de hoogste versie. |
| INACTIVE | Expliciet buiten gebruik gesteld, bijvoorbeeld vanwege een bug; mag niet meer draaien. |
| FUTURE RELEASE | Vereist nieuwere module-/databaseversies. ADMIN_OBJECTS mag dit automatisch vaststellen en rapporteren. |
| DEPRECATED | Te oud/achterhaald voor de huidige module-/databaseversies. ADMIN_OBJECTS mag dit automatisch vaststellen en rapporteren. |
| PENDING | Door inventarisatie gevonden registratie die verwerkt en beoordeeld moet worden. |
| ERROR | Fouttoestand, bijvoorbeeld ontbrekende vereiste objecten of Oracle INVALID. Kan door ADMIN_OBJECTS of beheerder worden gezet; wordt gerapporteerd. |

Deze betekenissen vervangen eerdere onjuiste interpretaties waarin INACTIVE uitsluitend 'boven maximumversie' betekende. De bestaande versievalidatielogica moet later aan dit functionele contract worden getoetst.

## Laatste voorstel van de gebruiker: evaluatiestatus

De gebruiker stelt voor OBJECT_STATUS te behouden en EVALUATION_STATUS plus de relevante vorige evaluatiestatus te beperken tot:

- ACCEPTED
- REJECTED
- PENDING

Dit geeft de beheerder een veto ongeacht OBJECT_STATUS. De assistent heeft dit als heldere ontwerprichting onderschreven. De bijbehorende DDL-constraints en code zijn nog niet aangepast.

Conceptuele uitvoeringsregel uit de laatste reactie:

- CURRENT + ACCEPTED: uitvoering toegestaan zolang de voorwaarden gelden.
- CURRENT + PENDING/REJECTED: uitvoering geblokkeerd.
- Andere OBJECT_STATUS: niet geselecteerd/toegestaan voor uitvoering.
- ACCEPTED maakt ACTIVE niet automatisch CURRENT en heft ERROR/INACTIVE/ongeschiktheid niet op.

CURRENT als 'aangewezen voor gebruik', ook tussen periodieke uitvoeringen, is de interpretatie van de assistent en verdient bevestiging in het functionele ontwerp. Gebruikstelemetrie is geen bewezen bestaande voorziening.

## Inventarisatie, wijzigingen en evaluatie

De gebruiker bepaalt:

- Bestaande beoordeelde registraties worden opnieuw getoetst, ook als ze CURRENT zijn.
- Bij een relevante wijziging, zoals een bijgewerkte versie of een ontbrekend object, gaat EVALUATION_STATUS naar PENDING.
- Een registratie waarvan EVALUATION_STATUS al PENDING is, wordt in volgende inventarisatierondes niet opnieuw ter overweging meegenomen.
- Hierdoor kan tijdelijk geen CURRENT én uitvoerbare query bestaan. Dit is een geaccepteerde uitkomst.

De laatste assistentreactie stelt aanvullend voor, nog niet afzonderlijk door de gebruiker bevestigd:

- PENDING overslaan voor heroverweging, maar fysieke waarnemingen en rapportage actueel houden zonder de open beoordeling te overschrijven.
- Geen automatische vervangende CURRENT-versie kiezen om continuïteit te forceren.
- REJECTED niet door een gewone inventarisatie opheffen; heropening vereist een expliciete aanleiding/handeling.
- Een expliciete INACTIVE-beslissing wegens een bug niet opheffen uitsluitend omdat versiebereiken passen.
