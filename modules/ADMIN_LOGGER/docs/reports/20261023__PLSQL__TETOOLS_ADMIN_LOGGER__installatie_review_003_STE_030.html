INS-003-01 Creation messages do not represent executed DDLCritical

Condition: Current source; a requested account, role, or tablespace is absent.[L0322–L0341]

Finding

The CREATE TABLESPACE, CREATE ROLE, CREATE USER and quota calls are comments. The live branches only print created or altered messages. No infrastructure is created by those branches.[L0322–L0341]

Recommended correction

Use an explicit PLAN or APPLY mode. PLAN must report planned actions. APPLY must execute validated statements and verify the resulting dictionary state before reporting success.[Proposal]

Acceptance check — not executed

Start with no TETOOLS account, role or dedicated tablespaces in a disposable Oracle test database. PLAN changes nothing. APPLY must create and verify the required components.[Proposal]

INS-003-02 The grant loop never executes a GRANTCritical

Condition: Current source, whenever the grant loop is reached.[L0035–L0102] [L0344–L0363]

Finding

c_grants contains 65 statements. The loop reads the name and calls checkmark; it never executes r_row.statement. Default checkmark values can mark an unexecuted grant successful.[L0035–L0102] [L0344–L0363] [GRANT]

Recommended correction

Execute each selected statement in APPLY mode, record the real outcome, then verify the direct system, role or object privilege. In PLAN mode retain NOT EXECUTED.[Proposal]

Acceptance check — not executed

Compare all selected statements with DBA_SYS_PRIVS, DBA_ROLE_PRIVS and DBA_TAB_PRIVS before and after. No row may report APPLIED without a real execution and matching postcondition.[Proposal]

INS-003-03 A tablespace name is compared with the number zeroHigh

Condition: The user, role and data tablespace all already exist.[L0014–L0014] [L0311–L0316]

Both OR expressions end with tblspce_idx = 0 instead of tblspce_idx_exists = 0. With the default nonnumeric name, reaching that comparison requires a character-to-number conversion that fails. Use tblspce_idx_exists = 0 in both expressions.[Proposal]

Acceptance check — not executed

INS-003-06 Installation failure is not a reliable client failureHigh

Condition: A required grant fails, or the internal-check exception is handled.[L0224–L0242] [L0365–L0408]

Finding

The aggregate feedback is printed, not raised as a final installation error. p_continue receives a value but does not control the result. The inner idx_internal_check handler prints and suppresses its error; normal-ended messages can follow. The current deliberate CONNECT failure can therefore coexist with normal PL/SQL completion if no earlier fault aborts the block.[L0224–L0242] [L0365–L0408]

Recommended correction

Compute required-step outcomes explicitly. Raise a final application error when a required step is not verified. Let optional failures produce a distinct warning status. Configure the script runner to stop and return a nonzero exit code on SQL failure.[Proposal]

Acceptance check — not executed

Inject a required failure and an optional failure separately. Required failure must return a failed client status; optional failure must return a clearly qualified result.[Proposal]

INS-003-18 Partial installation and original errors need explicit handlingHigh

Finding

ROLLBACK cannot undo preceding successful DDL. Generic loop handlers omit SQLCODE, SQLERRM and the error backtrace, and continue. idx returns 0 for an unknown key; that is outside the populated varray range. No such unknown manifest key exists now, but a future mismatch could cause a secondary error while checkmark runs inside a handler. DBMS_OUTPUT visibility also depends on the runner configuration.[L0198–L0211] [L0365–L0420] [COMMIT]

Recommended correction

Use a dedicated installation session, preflight before mutation, immediate structured error capture and a durable spool. Make unknown manifest names explicit internal errors without another failing lookup in their handler. Fail required actions clearly, preserve completed-step evidence and document resumable recovery rather than promising atomic rollback.[Proposal]

Acceptance check — not executed
