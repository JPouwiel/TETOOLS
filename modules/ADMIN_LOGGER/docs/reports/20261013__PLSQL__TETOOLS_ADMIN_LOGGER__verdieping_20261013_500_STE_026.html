V500-AN-01Session error logging can repeat the same failed lookupCritical

Analysis · Detailed explanation · Solution proposal

Baseline finding

load_session_details calls recovery and then raises the original exception again. session_details catches every error and calls LOG_ERROR_FORCE. That wrapper calls session_details again. A successful recovery can therefore produce a generic ERROR row. A persistent lookup or recovery failure can repeat the same path without a retry limit. The declared recovery flag is not used in the BODY.[V500-AN-01] [OAT] [OEX]

Causal sequence in the baseline

  1. A strict lookup raises a named registration error.[V500-AN-01]
  2. The current loader runs repair but then repeats the original RAISE.[V500-AN-01]
  3. The current wrapper logs through a procedure that performs the same lookup again.[V500-AN-01]
  4. If repair succeeded, this second lookup can work. If the underlying failure persists, it can repeat the path.[V500-AN-01]

Detailed answer to the follow-up question

The proposal moves repair ownership to session_details. The loader only validates and returns records or raises an exception. The wrapper captures the original stack, sets the existing busy flag, performs one repair, and reloads strictly. An error during that second load leaves the handler; it does not start another repair. Both success and failure clear the flag. Unexpected lookup errors propagate without destructive repair. The independent incident record is the durable evidence for the original serious registration error.[PROP]

Explicit proposal choice / assumption

One repair attempt per wrapper call. The existing public busy flag is treated as package-owned; callers must not write it. An external writer that keeps deleting rows can cause a later call to fail, but cannot turn this call into an unbounded logger loop.[PROP]
